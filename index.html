> // ARCHITECTURE_PIPELINE

6_STAGE_ISOLATION
01_HOST

Ingestion Coordinator

Host Space (Axum)
Listens on 127.0.0.1:3100, validates Bearer token authentication, performs tree-sitter AST syntax screening, and manages an async worker semaphore pool.
02_JAIL

Firecracker Jailer

Host Privilege Barrier
Drops root to unprivileged UID/GID 20001, applies PR_SET_NO_NEW_PRIVS, locks down dedicated chroot /srv/jailer/firecracker/<id>, and attaches cgroups v2.
03_VMM

KVM Hardware Boundary

Hypervisor Core
Interacts with Linux /dev/kvm ioctls to execute untrusted code in hardware CPU Ring 3. Restores memory snapshot in ~5ms with zero kernel boot latency.
04_INIT

cratera-agent (PID 1)

Guest Space Init
Serves as guest init process. Mounts ephemeral 256 MiB tmpfs in RAM, enforces Zero-NIC network denial, and communicates exclusively over virtual sockets.
05_SAND

Toolchain Sandbox

Compiler & Runtime
Executes compilers from languages.toml with strict POSIX RLIMIT_CPU, RLIMIT_NPROC (fork-bomb guard), and a kernel SIGKILL watchdog.
06_IPC

Precision Telemetry

Guest-Host Stream
Measures in-guest monotonic execution duration in microseconds and samples live RssAnon memory at 200μs intervals from /proc/[pid]/status before returning structured JSON verdicts over AF_VSOCK:52.

> ADDING A NEW LANGUAGE (ZERO ENGINE RECOMPILATION)

Cratera makes adding new programming languages and custom toolchains effortless. Rather than hardcoding compiler pipelines into the Rust hypervisor engine, all toolchains are defined declaratively in languages.toml. Cratera provides 4 flexible installation strategies so any runtime can be integrated in under 60 seconds:

1. install = "curl_tar" Directly downloads and extracts standalone binary release archives (e.g. Zig, Julia, Gleam).
2. install = "docker_image" Extracts compiler binaries directly from official Docker Hub / OCI images (e.g. Node, Swift, Dart).
3. install = "apt_core" Installs standard compiler packages directly via apt from Ubuntu repositories (e.g. GCC, Python, Java).
4. install = "docker_image_base" Uses an official image directly as the base rootfs build layer for maximum compatibility.
Example: Adding Gleam to languages.toml in 8 lines
languages.toml 
# Add to languages.toml - No Rust engine recompilation required
[gleam]
enabled = true
name = "Gleam"
source = "main.gleam"
compile = "gleam build --target=erlang"
run = "gleam run"
install = "curl_tar"
source_url = "https://github.com/gleam-lang/gleam/releases/download/v1.8.1/gleam-v1.8.1-x86_64-unknown-linux-musl.tar.gz"
After editing languages.toml, bake the runtime into the guest VM rootfs:
./scripts/build-rootfs.sh # or select [5] in cratera TUI

Systemd Service Deployment

Deploy Cratera as a supervised system daemon. The included unit file provides verified default settings designed for reliable out-of-the-box isolation across all major Linux distributions (Ubuntu, Debian, Fedora, Arch, RHEL).

✓ READY OUT OF THE BOX (NO MANUAL TUNING REQUIRED)
• Pre-hardened Security: Host eBPF network drop (IPAddressDeny=any), cgroups v2 resource delegation (Delegate=yes), and unprivileged Jailer isolation (UID 20001) are active by default.
• Safe & Non-Invasive: All defaults are self-contained in /opt/cratera. Custom ports, limits, or keys can be overridden anytime in /opt/cratera/.env without touching the unit file.
deploy/cratera.service 
[Unit]
Description=Cratera Firecracker harness judge service
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/opt/cratera
Environment=NODE_ENV=production
Environment=CRATERA_BIND=127.0.0.1:3100
Environment=CRATERA_FIRECRACKER=/usr/local/bin/firecracker
Environment=CRATERA_JAILER=/usr/local/bin/jailer
Environment=CRATERA_KERNEL=/opt/cratera/images/vmlinux.bin
Environment=CRATERA_ROOTFS=/opt/cratera/images/rootfs.ext4
Environment=CRATERA_WORK_DIR=/var/lib/cratera
Environment=CRATERA_USE_JAILER=1
Environment=CRATERA_JAIL_UID=20001
Environment=CRATERA_JAIL_GID=20001
Environment=CRATERA_USE_SNAPSHOT=1
Environment=CRATERA_SNAPSHOT_DIR=/opt/cratera/images/snapshot
EnvironmentFile=-/opt/cratera/.env
ExecStart=/opt/cratera/cratera
Restart=on-failure
RestartSec=3
LimitNOFILE=65536
Delegate=yes
KillMode=mixed

IPAddressDeny=any
IPAddressAllow=localhost

[Install]
WantedBy=multi-user.target
Directive / Variable Value Architectural & Security Function
User root Required on host for /dev/kvm ioctls and Jailer launcher (which drops to UID/GID 20001).
LimitNOFILE 65536 High file descriptor limit for concurrent microVM epolls, vsock sockets, and disk images.
Delegate yes cgroups v2 Delegation: Grants Cratera control over its cgroup subtree to enforce memory/CPU limits.
KillMode mixed Sends SIGTERM to coordinator process, then SIGKILL to any lingering microVM child processes.
IPAddressDeny any Host-level eBPF Sandboxing: Blocks all inbound and outbound IPv4/IPv6 internet traffic.
IPAddressAllow localhost Permits loopback (127.0.0.1, ::1) for local reverse proxies (Nginx/Caddy) and API clients.
CRATERA_USE_JAILER 1 Enables unprivileged Firecracker Jailer chroot, UID/GID 20001, and cgroups v2 sandbox isolation.
CRATERA_USE_SNAPSHOT 1 Restores microVM from memory snapshot in ~5ms, bypassing guest Linux kernel boot overhead.
sudo cp deploy/cratera.service /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl enable --now cratera.service

Manage, start, stop, or inspect the daemon via the cratera service CLI or Command Center Option [7]:

cratera service status # or: cratera service start / stop / restart

SCHEMA: FAQPAGE

> What is Cratera and how does it execute untrusted code?

▶

Cratera is a high-performance bare-metal microVM execution engine built in Rust using AWS Firecracker and Linux KVM (Kernel-based Virtual Machine). Unlike standard container sandboxes that share the host operating system kernel, Cratera runs every execution job inside a dedicated, hardware-isolated microVM in CPU Ring 3 privilege mode.

This ensures complete defense against Linux kernel exploits, container breakouts, and multi-tenant cross-contamination.

> How does Cratera achieve sub-5ms snapshot restore latency?

▶

Traditional virtual machines take seconds to boot the guest operating system. Cratera overcomes this by pre-booting a minimal Linux guest kernel, initializing the in-guest cratera-agent, and capturing a memory snapshot to RAM.

When an evaluation payload arrives, Cratera restores the microVM snapshot in approximately 5 milliseconds, immediately dispatching execution without boot overhead.

> How does Cratera differ from Docker containers and WebAssembly sandboxes?

▶

Docker/LXC: Relies on Linux namespaces and cgroups on a shared host kernel. Any kernel bug (e.g. dirty COW, io_uring privilege escalation) can compromise the entire host machine.

WebAssembly (Wasm): Provides great isolation and startup speed but cannot run arbitrary native C/C++ binaries, standard Python packages with C-extensions, or standard JVM/CLR runtimes without compilation modifications.

Cratera: Delivers true hardware virtualization (Intel VT-x / AMD-V) with full POSIX compatibility for 30+ native language toolchains at container-like sub-millisecond latencies.

> How does Cratera prevent network exfiltration and fork bombs?

▶

Cratera implements a defense-in-depth isolation boundary:

Zero-NIC: MicroVMs are launched without any virtual network interfaces (no tap/tun, no eth0). In addition, systemd eBPF IP deny rules block raw packet generation.

Resource Limits: Fork bombs and infinite loops are neutralized using POSIX RLIMIT_NPROC, RLIMIT_CPU, and cgroups v2 memory controllers, backed by an asynchronous hypervisor SIGKILL watchdog.

> How easy is it to add new programming languages to Cratera?

▶

Adding new toolchains requires zero Rust engine recompilation. All compiler commands, source filenames, runtime paths, and installation strategies (apt packages, official Docker image extraction, or curl release archives) are declared in languages.toml. You can configure and bake a new runtime into the rootfs image in under 60 seconds.

> How is Cratera deployed as a systemd service?

▶

Cratera ships with a systemd unit (deploy/cratera.service). It configures host-level eBPF kernel network sandboxing (IPAddressDeny=any, IPAddressAllow=localhost), cgroups v2 resource delegation (Delegate=yes), unprivileged Firecracker Jailer chroot (UID/GID 20001), 65K open file descriptors (LimitNOFILE=65536), and automatic restart recovery.
